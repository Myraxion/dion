# List 递归性能调研（归档）

本文件于 2026-10-11 归档，记录 List 递归性能优化的调研、决策和验收。当前行为契约以[核心规范](../spec.md)为准；归档内容不代表待办事项。

## 已确认的范围

- 优化目标是缩短单次完整递归扫描耗时。
- 保持当前查询范围、记录与错误排序、链接边界、错误处理和文本/JSON 内容。
- 本轮不增加缓存或新的默认排除目录。
- 先测量当前 Release 基线，再根据证据决定优化方案；用户已同意比较终端输出与丢弃输出。
- 用户报告 D 盘根目录递归耗时为 88.810 秒，来自终端提示符计时；用户已比较多个版本，速度差异不大。完整命令、轮次和终端配置未记录，因此该数字是体验观察，不是可直接比较的工程基线。

## 已核实的代码事实

- `src/listing.rs::collect_directory` 串行枚举并递归进入子目录。
- 每个目录都会调用 `storage::read` 读取 `descript.ion`；不存在时，`src/storage.rs` 还会查询父目录元数据以区分父目录消失与备注文件缺失。
- 所有目录都建立目录名称集合；即使该目录没有备注记录，也会付出 UTF-16 名称分配和名称比较成本。
- 普通递归也先保留完整 `Directory` 树，扫描结束后再展开为记录列表；没有相关记录的空分支也会保留。
- Windows 上 `DirEntry::file_type()` 使用枚举携带的信息，无额外系统调用，见 [Rust 官方文档](https://doc.rust-lang.org/std/fs/struct.DirEntry.html#method.file_type)。
- 无备注的中间目录仍需遍历，其后代可能存在备注；不能因为本目录无备注而停止扫描。
- 当前 Release 使用 `opt-level = "s"`，需要实测才能判断速度优化等级是否有收益。

## 测量方法

- 从当前源码执行 `cargo build --release --locked`，记录源码提交、二进制哈希和参数。
- 用 `list D:\ -r` 测量当前默认查询范围；stdout 和 stderr 异步读取丢弃，仅保留字节数及 SHA-256，不记录用户备注内容。
- 记录壁钟、进程生命周期、进程用户态与内核态 CPU 时间及退出码。退出码 1 可能是正常完成扫描并汇总诊断，不当作测量工具失败。
- 连续执行用于观察温运行变化，不清空系统文件缓存，不将首次调用称为磁盘冷启动。
- 临时诊断副本用于累计枚举、备注读取、解析排序耗时与访问计数；诊断版本的耗时包含探针开销，不能替代正式产物基线。
- 自动化执行环境不能等价复现用户终端的渲染与滚动开销；终端差异需结合用户原终端中的同参数测量评估。
- 已核实 D 盘是本地 NTFS 固定卷，物理介质类型尚未核实；现有单目录 100/10,000 条记录基准不能代表全盘递归工作负载。

## 调研阶段的初步候选

1. 减少无备注目录的重复文件系统访问。需要明确枚举后目录或备注文件变化的处理，不直接删除所有调用场景中的父目录检查。
2. 按有效备注记录需要建立名称集合，扫描完成后不保留没有相关记录的空分支。此方案减少 CPU 和内存工作，不减少必须访问的目录。
3. 比较有限并发的递归遍历，继续按契约顺序合并记录和诊断。收益取决于访问等待、介质和并发程度。
4. 比较 Release 的速度优化等级与当前配置，同时记录 exe 体积。

### 据此调整的建议

首选是在成功完成目录枚举时，同时观察备注文件是否存在：未发现时不再尝试打开缺失的备注文件，也不再对这个已枚举目录做后续父目录元数据检查。对发现的备注文件仍使用原有读取和解析行为，保留读取错误及记录诊断；无备注目录仍继续递归。此前候选“减少查找集合和空目录树”不是当前首要提速手段，单独消除最终展开的收益尤其有限。

用户已确认以下行为边界：枚举之后才新建的备注文件可能到下一次调用才被发现；枚举之后目录消失时，无备注路径也不会通过额外的父目录检查补报该变化。当前实现也不提供整个目录树的原子快照，但仍不能把不同的竞态观察点称为完全相同的行为。正常静态目录上的查询范围、记录与错误顺序、权限和链接行为应保持。

69.654 秒是该诊断运行整个读取阶段的成本量级，不是承诺能全部消除的时间。发现备注文件会增加名称检查成本，已有备注仍需读取；枚举自身约 50 秒也不能通过此方案消除。只去掉父目录检查可触及的阶段量级约为 37 秒，复用枚举信息同时避免缺失文件打开才可能覆盖更大部分。实际收益必须比较完成方案后的 Release 实测。

有限并发和更大枚举缓冲作为后续候选。本机 Rust 1.99.0（`b940084d7`）的标准库源码确认 `read_dir` 已使用 `FindFirstFileExW`、`FindExInfoBasic`、`FindExSearchNameMatch`，附加 flags 为 0；仅改用该 API 或 Basic 信息级别是重复现有实现。`FIND_FIRST_EX_LARGE_FETCH` 才是可实验的新增差异，但 [微软文档](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirstfileexw) 只说明可能提高性能，应评估额外 FFI 和句柄管理成本。目录过滤 `FindExSearchLimitToDirectories` 是[建议性过滤](https://learn.microsoft.com/en-us/windows/win32/api/minwinbase/ne-minwinbase-findex_search_ops)，还不能同时完成普通备注文件的发现，不作为首选。

## 已确认方案与实施

- 用户接受以本次目录枚举结果决定是否读取备注文件的观察边界。
- 实施在共用目录采集函数中增加备注文件发现；按既有 Windows 名称比较规则匹配，不按文件类型过滤，以保留同名目录、文件链接和读取失败的行为。
- 未发现备注文件时直接视为无记录，继续既有子目录递归；不改变 `storage::read`，其他命令和已发现文件的父目录检查仍保持。
- 验证使用真实 CLI、统一检查入口及同参数 Release 全盘对照；通过字节数、输出 SHA-256 和退出码检查查询结果。
